# Windows candidate qualification notes

The retained native VM reproduced the first source build's empty probe result: the application started, but configure silently omitted Python scripting after `sipbuild` could not import its build-only prerequisites. `build.py` now prepares pinned `packaging` and `setuptools` wheels in a private build directory, imports the SDK SIP/PyQt builder before configure, requires the SIP/PyQt/Python CMake packages, and requires an installed pykrita DLL. The retained Windows11 VM completed this source rebuild with Python scripting enabled. Actual art/menu/font checks passed; final package qualification remains separate.

The existing packaging helper delegates to upstream `package-complete.py`, which collects LLVM-MinGW runtime DLLs from the architecture-specific compiler directory. A manual launch without this build PATH demonstrated why final relocation testing must remove SDK/compiler PATH dependencies.

The upstream packaging helper ordinarily expects a Windows SDK redistributable directory. The reviewed Windows10/11-only adaptation uses `windeployqt --no-system-d3d-compiler` and the OS-provided D3DCompiler_47.dll. Microsoft's C++ team documents that DLL as a system component on Windows8.1 and later: https://devblogs.microsoft.com/cppblog/on-c-amp-remappable-shader/ . Qt documents using the operating system's compiler with ANGLE on recent Windows: https://wiki.qt.io/Qt-5-on-Windows-ANGLE-and-OpenGL . The helper now makes a private, exact-context adaptation of the upstream deployment calls and checks the pinned executable advertises this option. Actual Windows11 CLI verification and System32-only DLL loading passed; package rendering is not yet qualified. It requires actual OS-origin module evidence and ANGLE rendering checks; do not copy arbitrary System32 DLLs or infer graphics support from startup alone.

`graphics-probe.py` now supplies a Windows-native graphics gate. Its SDK diagnostic passed in the retained Windows11 VM: ANGLE D3D11 WARP, shader compilation/linking, triangle rasterization and exact `[255,0,0,255]` readback, with the operating system D3D compiler and candidate Qt/ANGLE/Python module origins recorded. This is software rendering, not physical GPU coverage. Final mode requires the candidate embedded interpreter, an exact archive, archive-byte matches for loaded candidate modules, no external DLL directory, and a relocated/installed runtime scope. SDK mode is explicitly unqualified.

The original probe used `os._exit` and recorded an access violation after its functional receipt. An independent normal Qt-close trial passed with exit code0 and all original art/font/menu checks; the original crash remains retained. The shared probe now keeps document/node wrappers alive through final capture, waits for document jobs, closes its QA-created documents/windows, and requests the Qt event loop exit with the test result. Lifecycle fields and the external process return code must both pass. This improves the test lifecycle; it does not claim a proven sole cause for the original forced-exit fault.

Package preparation preserves the maintained embedded interpreter entry points and converts SDK-contained `_pth` entries into relative paths, rejecting external paths and unexpected import directives. Four focused path tests pass; final package execution still must prove actual interpreter/module origins with SDK paths removed. Inventory names include the `Flapart-Studio/` archive prefix.
